# Code Review Skill

Reviewer 执行代码评审时的参考规范。

## 评审方法论

1. **先读上下文**：`feature.md`、`design.md`、OpenAPI、相关 `scenario`，理解变更的业务目的
2. **先看测试**：测试是否覆盖了主要路径和边界情况
3. **再看业务逻辑**：对照设计文档检查实现是否一致
4. **最后看细节**：命名、格式、错误处理、安全
5. **大型 PR 策略**：>500 行时，优先评审核心路径和接口契约，细节可标记为 `[SUGGESTION]`

## 评审 checklist

### 1. 代码规范

- [ ] TypeScript 严格模式通过（无 `any` 滥用）
- [ ] 命名清晰一致（变量/函数/类名表达意图）
- [ ] 无硬编码配置（环境变量 / 配置文件管理）
- [ ] 错误处理完整（异常捕获、错误码、不吞异常）
- [ ] 日志适当（不打印敏感信息、关键路径有日志）

### 2. 设计一致性

- [ ] 实现与 `feature.md` / `design.md` 一致
- [ ] API 与 OpenAPI 契约一致（路径、参数、响应格式、错误码）
- [ ] 组件分层符合 CDD（Component-Driven Development）
- [ ] 无范围蔓延（PR 只做声明的事，不夹带无关变更）
- [ ] **Scenario 一致性**：本 PR 触及的代码路径是否涉及 `docs/architecture/scenarios/` 中的 scenario？若是，`scenarios/` 是否已同步更新？

### 3. 测试覆盖与质量

- [ ] 业务验证路径有测试
- [ ] 权限检查有测试
- [ ] 错误分支有测试（400 / 401 / 403 / 404 / 500）
- [ ] 边界值覆盖（空值、极限长度、并发、越界）
- [ ] 测试数据使用工厂函数，无魔法值硬编码
- [ ] Mock 合理，测试之间无状态泄漏
- [ ] 行覆盖率 >= 80%（CI 门槛）

### 4. 安全

逐项确认：

- [ ] 敏感信息（密码 / token / API key）不硬编码、不打印日志
- [ ] 输入校验完备：所有接口入口有 Zod schema 或等效校验
- [ ] 权限检查 deny-by-default，最小权限原则
- [ ] SQL 注入 / NoSQL 注入 / XSS 风险已处理
- [ ] CSRF / 点击劫持防护已评估
- [ ] 新增外部依赖已评估安全影响（已知漏洞、维护状态）
- [ ] 错误响应脱敏（不暴露 DB 连接串、堆栈详情、内部路径）
- [ ] 参数化查询，禁止字符串拼接 SQL
- [ ] CORS 限制来源（不开放 `*`）
- [ ] Rate Limiting 已配置（通用 + 敏感操作独立限制）
- [ ] JWT Secret 长度 >= 256 bit，access token 过期 <= 1h
- [ ] 密码哈希使用 bcrypt（rounds >= 12）或 Argon2id

### 5. 性能与效率

- [ ] 算法复杂度合理（无嵌套循环处理大数据量）
- [ ] 无 N+1 查询（数据库访问批量处理）
- [ ] 异步操作无阻塞（I/O 操作不阻塞主线程）
- [ ] 无内存泄漏（事件监听清理、闭包引用释放）
- [ ] 资源使用合理（连接池、文件句柄及时释放）

### 6. 可维护性

- [ ] 函数/类职责单一（SRP）
- [ ] 函数长度合理（>50 行需审视，>80 行建议拆分）
- [ ] 圈复杂度可控（>10 需审视，考虑拆分或策略模式）
- [ ] 无重复代码（DRY）
- [ ] 无死代码 / 未使用的变量和导入
- [ ] 注释解释 WHY 而非 WHAT（非 obvious 的约束、业务规则）
- [ ] 相关文档（README、API 文档）已同步更新

### 7. 前端专项（如适用）

- [ ] UI/UX 与 design.md / 设计稿一致
- [ ] 响应式布局适配（移动端/桌面端）
- [ ] 无障碍（a11y）：表单有 label、图片有 alt、键盘可导航
- [ ] 用户输入转义输出（防御 XSS）
- [ ] 禁止 `dangerouslySetInnerHTML` 直接渲染未过滤内容
- [ ] 状态管理合理（服务端状态 vs 客户端状态区分）
- [ ] 渲染性能：无不必要的重渲染、大数据列表有虚拟化

### 8. 后端专项（如适用）

- [ ] API 设计符合 RESTful 规范或项目约定
- [ ] 并发安全：共享状态有锁 / 原子操作 / 无竞态条件
- [ ] 数据库事务边界正确（跨表操作有事务包裹）
- [ ] 查询效率：有适当索引、无全表扫描、聚合查询优化
- [ ] 缓存策略合理（缓存 Key 设计、失效策略、缓存穿透防护）
- [ ] 软删除优先于物理删除

## PR 规模检查

| 级别 | 变更行数 | 处理方式 |
|------|---------|----------|
| **目标** | < 500 行 | 理想大小，可逐行评审 |
| **警告** | 500--800 行 | 须在 PR description 中说明未拆分原因 |
| **上限** | > 800 行 | **必须拆分**；Reviewer 可拒绝评审 |

> 统计方式：`git diff --stat origin/main...HEAD -- ':!*.md' ':!*.yaml' ':!*.json' ':!docs/' ':!.claude/'` 的插入+删除行数之和。文档/配置变更不计入。

## 结论

| 结论 | 含义 | 处理 |
|------|------|------|
| **Approved** | 无阻塞问题 | 留 PR comment，用户可验收 |
| **Approved with comments** | 非阻塞建议 | Developer 视情况处理 |
| **Changes Requested** | 有必须修改的问题 | 列出问题；Developer 修完 re-request review |

## 必须修改的问题（4 条红线）

命中以下任一即给出 **Changes Requested**，并在评论首条标注 `[BLOCKED]`：

1. P0 测试失败或覆盖率不达标
2. 发现安全漏洞
3. 设计与实现严重偏离且无合理解释
4. 关键逻辑无测试覆盖

## 评论格式

- **必须修改**：`[MUST]` + 具体文件/行号 + 修改建议 + 推荐 diff（如有）
- **严重阻塞**：`[BLOCKED]` + 红线原因（用于 4 条红线命中时）
- **建议修改**：`[SUGGESTION]` + 理由
- **问题澄清**：`[QUESTION]`

## 评审输出

不写独立 `.md` 文件。结论直接作为 PR review comment。
