# Design Review Skill

Reviewer 执行架构评审时的快速参考。

## 何时执行 / 跳过

| 场景 | 处理 |
|------|------|
| 引入新技术 / 新模块 / 新表 | 必审 |
| 改现有路由 / API 契约 | 必审 |
| 复用既有模式 + 纯页面拼装 | 可跳过，Designer 自审 |
| 用户问"架构靠谱吗" | 必审 |

## 变更分级与评审深度

评审深度应与变更级别匹配（参见 Designer 的 T1/T2/T3 分级）：

| 级别 | 定义 | 评审深度 |
|------|------|---------|
| **T1** | 语法/表述修正，无架构影响 | **无需**架构评审 |
| **T2** | scenario 步骤/流程调整，契约和 Actor 不变 | 轻量化：一致性 + 复用检查 |
| **T3** | 契约变更、Actor 变更、架构级变更 | 完整：全部维度逐项检查 |

## 评审维度

### 1. 一致性

数据模型 / API / 架构分层是否符合现有约定。

检查清单：

- [ ] 数据模型命名与现有表一致
- [ ] API 路径风格与 OpenAPI 现有端点一致
- [ ] 错误码 / 响应格式与现有 API 一致
- [ ] 架构分层符合项目约定（如 CDD）

### 2. 可行性 & 风险

新依赖有充分理由；风险可识别 + 可缓解。

检查清单：

- [ ] 核心依赖（框架/ORM/认证方案）的必要性已说明，有选型对比
- [ ] 工具库引入有必要性说明（轻量检查，非核心依赖不必强行对比）
- [ ] 风险已识别并有缓解方案（附风险等级：高/中/低）
- [ ] 回滚方案已明确（T3 变更必须）

### 3. 复用

检查清单：

- [ ] 已有组件 / 工具函数 / 相似页面已检索
- [ ] 新组件的必要性已说明（不是已有组件的变体）
- [ ] 是否引入了与现有功能重复的数据模型或 API

### 4. 安全与合规

架构阶段识别安全风险，避免代码写完后返工。

检查清单：

- [ ] 新模块的权限模型已评估（最小权限原则、deny-by-default）
- [ ] 敏感数据流向已梳理（存储/传输/返回前端）
- [ ] 输入攻击面已识别（新增端点的注入/越权风险）
- [ ] 外部依赖的安全影响已评估（已知漏洞、维护状态）

### 5. 可扩展性与可观测性

检查清单：

- [ ] 性能瓶颈已预判（数据量增长、并发场景）
- [ ] 故障场景与降级策略已定义（T3 必须）
- [ ] 新增监控/日志/告警点已明确（T3 必须）
- [ ] 数据一致性方案已说明（如有分布式/异步操作）

### 6. 业务影响（minor 项必填维度）

每条 [CONCERN] / [SUGGESTION] 都必须能回答三个问题，否则不算合格评审：

- [ ] **业务影响**：如果现在不处理，会产生什么业务/技术后果？必须说人话：什么场景会出问题、最坏情况是什么
- [ ] **处理成本**：估算工作量（≤ 1 行 / ≤ 1 小时 / 跨 ft 基础设施改造）
- [ ] **推荐处置**：ft 内必做 / ft 外延后（登记 TD）/ 不处理

**「ft 内必做」识别标准**（满足任一）：

- 处理成本 ≤ 半天
- 与本 ft 决策直接相关（不做会破坏 ft 内部一致性）
- 业务影响为「生产事故」或「安全隐患」

**「ft 外延后」识别标准**（满足任一）：

- 跨 ft 基础设施决策（ORM、Redis、OTel 接入）
- 独立 Epic 范围
- 运维/治理类（审计保留策略、PII 清理 job）

**「不处理」需记录理由**（如：理论可能但实际不构成实质风险）。

## 评审交互规范

评审意见按以下格式分类，便于 Designer 和 Orchestrator 识别优先级：

| 标记 | 含义 | Designer 处理 |
|------|------|--------------|
| `[BLOCKER]` | 阻塞架构推进的问题 | 必须解决后才能进入下一步 |
| `[CONCERN]` | 风险点，需记录并跟踪缓解方案 | 需在 design.md 或 architecture-review.md 中回应 |
| `[SUGGESTION]` | 非阻塞建议 | 可视情况采纳或记录不采纳理由 |

**每条 [CONCERN] / [SUGGESTION] 必填三段式**：

```markdown
### [CONCERN-N1] {问题简述}

- **业务影响**：{如果现在不处理，会产生什么业务/技术后果}
- **处理成本**：{估算工作量}
- **推荐处置**：
  - [ ] **ft 内必做**（低成本、高价值、本 ft 必须修）
  - [ ] **ft 外延后**（独立基础设施 / 跨 ft 决策 / 运维 → 登记为 TD）
  - [ ] **不处理**（不构成实质风险，记录理由）
- **结论**：{ft 内必做 / 延后为 TD / 不处理}
```

## 结论

| 结论 | 含义 | 处理 |
|------|------|------|
| **Approved** | 无阻塞问题 | Designer 可进入设计方案审批 |
| **Approved with minor** | 仅有 `[SUGGESTION]` 或「ft 外延后」类 [CONCERN] | 进入用户审批 Gate；minor 项分类后展示给用户决策 |
| **Changes Requested** | 有 `[BLOCKER]` 或「ft 内必做」类 [CONCERN] 未解决 | Designer 返工，解决后重新评审 |

**不要因为评审意见就拉用户**。只有以下场景才上报，触发架构审批 Gate：

- 需要用户决策的架构层面改动（新技术选型 / 改路由 / 改 API 契约）
- 风险等级为"高"且缓解方案需用户确认资源投入
